FIRST APPLICATION

Connect an app, then give people access.

authd handles sign-in for your applications. Start by connecting BDC Maps below. You do not need to configure every section in this interface.

What the pieces mean

User
A person, with one authd password and optional authenticator.
Role / group
A named assignment such as bdcmaps-viewer. The groups and roles claims expose the same assigned role names, not separate group directories.
Permission
An operation an app has been written to check. Useful for scope-aware apps; not required for BDC’s existing role mapping.
Client
An application, such as BDC Maps. Its client secret is the backend’s credential, not a user’s password.
Issuer
authd’s public HTTPS address: {{.Issuer}}. A Unix socket is only the internal connection from the reverse proxy.
Callback / redirect URI
The app’s endpoint that receives the sign-in result. It is not an authd page.
Scope
What the app asks authd to release. An allowed scope is not automatically requested or granted.

There are three different kinds of “admin”: PostgreSQL administration, authd’s system-admin, and an application’s administrator. Granting one does not automatically grant the others.

The app still controls its own customer, tenant, PBX, project, room, or other resource memberships. Signing in proves identity; it does not create those relationships.

First BDC Maps login

No new permission catalog needed

  1. Create the BDC roles

    Create bdcmaps-administrator, bdcmaps-reviewer, bdcmaps-planner, and bdcmaps-viewer. Leave permission checkboxes empty for this integration. BDC maps these exact group names to its own built-in roles.

  2. Create or edit a test user

    Give the user an email address and assign the intended BDC role. Do not give ordinary BDC users system-admin. If Require password change is selected, they must finish that on Account before restarting BDC sign-in.

  3. Register BDC Maps

    Client ID bdcmaps; name BDC Maps; type Confidential; access token lifetime 300 seconds. Register the application’s exact /auth/callback URL. Allow openid profile email groups. Leave application permissions, offline access, refresh tokens, and optional logout URLs alone for the first connection.

    Leave Require MFA off only for the initial connectivity test; enroll intended users in Account → Authenticator and enable it before granting access that requires MFA.

  4. Save the client secret once

    After Register client, copy the secret into BDC’s OIDC_CLIENT_SECRET runtime secret. It does not belong in authd’s environment. The page is a one-time reveal; rotate only when you can update BDC too.

  5. Configure the BDC side

    Set issuer to {{.Issuer}}, client ID to bdcmaps, and its callback to the same registered URL. Request openid profile email groups, set group claim to groups, and map the four role names above to BDC’s administrator/reviewer/planner/viewer lists.

    For a new BDC install, its own installer must configure OIDC and link the first administrator by exact issuer + subject. Edit the authd user to find that subject. For existing BDC, use its OIDC administration settings. BDC provisioning policy still controls whether new identities are admitted.

  6. Start sign-in from BDC, not from this admin page

    BDC redirects to authd; you sign in; authd returns a code to BDC; BDC validates it and creates its own session. Verify the expected BDC role with both an administrator and a restricted test user. A successful authd sign-in alone does not prove the BDC callback works.

Two access models, not two jobs to do for every app.

BDC today: assign roles here and map their names in BDC. A scope-aware app: define the permission in that app, bundle it in a role, assign the role, allow the scope on its client, and request/check it in the app. Inventing permission names here does not change an application’s code.

This release has no separate per-client allowed-users list or per-client role-name filter. Identity-only clients can authenticate any enabled user. A client allowed to request groups or roles can receive all of that user’s assigned role names. Do not use those claims with a client that should not see them.

When something fails

Form refused before anything saves
Reload the form through the public authd URL. Check proxy Host/forwarding/cookies. Native form pages must return Referrer-Policy: origin; no-referrer can make the browser send Origin: null. Do not fix this by disabling CSRF or allowing null origins.
Admin page opens, save is denied
Writes require a sign-in within 10 minutes. Sign in again, then reopen the form. Verify that this user still has system.admin.
Invalid redirect or client
Compare BDC’s issuer, client ID, exact callback and secret with the saved registration. A trailing slash, different host, or old rotated secret matters.
Invalid scope / access denied
The app requested an unknown or disallowed scope, or the user lacks a requested application permission. For the BDC profile use the four identity scopes above; do not request every permission in the catalog.
Login succeeds, BDC role is wrong
Check assigned roles, BDC’s requested groups scope and its exact group mappings. Start a new BDC login; an old BDC cookie can retain old authority. An unmatched group may fall back to BDC’s configured default role.
MFA required, but user has no code
Enroll an authenticator from Account first. An administrator can reset a lost factor after verifying the person’s identity. Resetting a factor is not the same as satisfying an MFA-required client.
User disabled here but app still open
authd blocks new sign-ins/refreshes; the app may still trust its own cookie. Revoke its local sessions too. Back-channel logout is not implemented.
Server unavailable / error reference
Use the timestamp and request reference to correlate daemon and proxy logs. Keep credentials and token-bearing URLs out of tickets. Database health is not the same as successful application sign-in.
