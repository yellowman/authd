{{define "view-help"}}
{{if eq .View "users"}}

Users are people, not applications.

Create one account per person, then assign roles. A user can sign in with no roles; the application still decides whether that identity has access. You do not create another password for each app.

Connecting BDC Maps? Give each BDC user an email and the appropriate bdcmaps-… role.

{{else if eq .View "roles"}}

A role is a bundle you assign to people.

For the current BDC integration, the role’s exact name is sent as an OIDC group and mapped by BDC. A role may have no permissions. For newer scope-aware apps, a role bundles individual permission scopes.

system-admin controls authd. Use a separate bdcmaps-administrator role for BDC administration. After saving a role, assign it to users.

{{else if eq .View "permissions"}}

A permission names an operation the app understands.

Creating reports.export does not add an export button or teach any app to authorize it. The application must implement the check. You can skip this section for BDC’s existing group mapping.

For a scope-aware app: create the agreed permission, add it to a role, assign the role to the user, allow it on the client, and have the app request it. Missing user permission denies that authorization request; it is not silently dropped.

{{else if eq .View "clients"}}

A client is an application allowed to ask authd for sign-in.

Register BDC Maps here, then copy the connection details into BDC. This form alone does not configure BDC or give all authd users a BDC role. First BDC login walkthrough.

{{else if eq .View "sessions"}}

These are sign-ins at authd, not every app’s session.

Revoking one stops reuse of that authd session and its associated refresh grants. Already-issued access tokens expire normally. An app can retain its own session cookie; remove access there too when immediate lockout is required.

{{else if eq .View "keys"}}

Signing keys let applications verify authd’s tokens.

authd creates the initial signing key automatically. You do not need to rotate it to connect an app. The public key set is at {{.Issuer}}/jwks.json; never give an application authd’s master key or private signing key.

The master key encrypts stored secrets; rotating a signing key is a different operation. Old public verification keys remain published. This screen does not delete them.

{{else}}

Audit records show what authd did.

Use events to distinguish a successful sign-in from a client or permission failure. These are authd’s events, not BDC’s callback log. Copy the error reference and timestamp for an operator; do not copy passwords, tokens, browser cookies, or client secrets.

{{end}}
