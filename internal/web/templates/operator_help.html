{{define "view-help"}}
{{if eq .View "users"}}

Users are people, not applications.

Create one account per person, then assign roles. A user can sign in with no roles; the application still decides whether that identity has access. You do not create another password for each app.

{{else if eq .View "roles"}}

A role is a bundle you assign to people.

An app may map a role's exact name from groups or roles, or check the permissions bundled in it. A role may have no permissions. After saving a role, assign it to users.

system-admin controls authd, not every application. Use app-qualified names such as inventory-viewer for application roles.

{{else if eq .View "permissions"}}

A permission names an operation the app understands.

Creating inventory.items.read does not teach an app to authorize it. The application must implement the check. Skip this section for identity-only or groups-only integrations.

For a scope-aware app: create the agreed permission, include it in a role, assign that role, allow the scope on the client, and have the app request and check it. Missing user permission denies the request.

{{else if eq .View "clients"}}

A client is an application allowed to ask authd for sign-in.

Register the app, then copy its saved connection details into that app's OIDC settings. This form alone does not configure the app or assign people access. Adding an app walkthrough.

{{else if eq .View "sessions"}}

These are sign-ins at authd, not every app’s session.

Revoking one stops reuse of that authd session and its associated refresh grants. Already-issued access tokens expire normally. An app may keep its own cookie; revoke its local sessions too when immediate lockout is required.

{{else if eq .View "keys"}}

Signing keys let applications verify authd’s tokens.

authd creates the initial key automatically. You do not need to rotate it to connect an app. Public keys are at {{.Issuer}}/jwks.json. Never give an application the master key or a private signing key.

The master key encrypts stored secrets; signing-key rotation is a different operation. Old public verification keys remain published. This screen does not delete them.

{{else}}

Audit records show what authd did.

These are authd events, not an application's callback log. Correlate the error reference and timestamp; do not copy passwords, tokens, browser cookies or client secrets into a ticket.

{{end}}
